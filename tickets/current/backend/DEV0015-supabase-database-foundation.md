## Objective and context

Establish repeatable PostgreSQL schema, secure runtime access and seeded catalogue data before connecting the frontend to a shared backend. Implement the [database recommendation and phases](../../../docs/mvp-spec.md#database-provider-recommendation--19-september-2026) and [migration contract](../../../docs/mvp-spec.md#migrations-environments-and-seed-boundaries). Supabase is the recommended provider, not yet a provisioned account.

## Scope and non-goals

- In scope: pinned Supabase local tooling, Drizzle/Postgres driver, the sole `supabase` configuration/migration/policy/seed history, server-only environment/connection modules and Drizzle table mappings under `src/server/db`, separate runtime/migration roles, base identity/run/organization/venue/class/membership tables, constraints/indexes and deterministic catalogue seeds; redacted environment example and real setup/test commands.
- Out of scope: the general server import/layer enforcement owned by DEV0025; browser sign-in, exposing private business APIs, migrating localStorage, challenge settlement/financial tables, payments, visits, event publication, production deployment or paid upgrades. Do not rewrite the frontend or create every future table now.

## Expected behavior and edge cases

A clean local database can be migrated and seeded repeatedly without duplicate catalogue entities. A runtime connection cannot modify schema, bypass row policies or access private rows without valid context. Unclaimed demo profiles have no login/role authority. Organization and venue types support cafés as well as gyms; trainer affiliations can span venues. Every run-scoped relationship rejects cross-run references. Missing/malformed configuration fails explicitly without logging credentials. SQL constraints reject negative/excessive amounts, invalid times and duplicate membership identities where those fields exist.

## Assumptions, decisions, and dependencies

The pinned CLI runs through the project package manager and requires a running Docker-compatible container runtime. Use `supabase/migrations/` as the only applied migration history and Drizzle for typed server queries. Runtime app tables live in an unexposed `app` schema, with default-deny row-level security (RLS) and least-privilege roles; policies for authenticated feature access arrive in subsequent slices. Implement [DEV0025](DEV0025-nextjs-backend-boundary.md) concurrently from the first server configuration/database edit. DEV0015 owns database dependencies, SQL artifacts, server-only connection configuration, Drizzle table mappings and database integration evidence. DEV0025 owns the server-only/import rules that constrain them. Feature tickets own the repositories and services that query those mappings; DEV0015 must not pre-build catalogue, identity, draft or booking repositories.

The completed [DEV0031 boundary](../../archive/frontend/DEV0031-preview-data-and-domain-boundaries.md) is the frontend baseline. Database rows and inferred Drizzle row types stay server-only. Later repositories map selected rows into explicit `src/domain` or response contracts; they never import `src/features/preview`, expose raw row types to features, or silently replace preview data.

## Foundation schema contract

### Shared SQL conventions

- All application tables use the `app` schema. Entity tables use UUID primary keys generated with `gen_random_uuid()`; relationship tables use the composite UUID business keys stated below. Audit and interval fields use `timestamptz`; `created_at`/`updated_at` default to `now()` and a shared trigger advances `updated_at` on change. Slugs are lowercase kebab-case checked by `^[a-z0-9]+(?:-[a-z0-9]+)*$`. Core run/catalogue records are retired or disabled through status fields rather than hard-deleted.
- Every run-scoped entity with its own UUID identifier also has `unique (run_id, id)`; relationship tables use the composite business key as their primary key. Relationships that must stay in one run use composite foreign keys containing `run_id`; a globally unique UUID alone is not sufficient proof of run membership.
- Activity values are limited to `Running`, `Strength`, `Muay Thai` and `Yoga`. Venue activity arrays are non-empty and may contain only those values. Status/kind/role columns use `text` plus named `check` constraints in this foundation rather than PostgreSQL enums, so later additions use ordinary reviewed migrations.
- Monetary values use `numeric(20,0)` base units and must be between `0` and `18446744073709551615`, inclusive. Drizzle/server boundaries serialize them as decimal strings and never JavaScript numbers. DEV0015 stores only class catalogue prices; it creates no balance, payment, refund, pool or ledger rows.
- Scheduled records store UTC `timestamptz` instants plus an IANA timezone snapshot. Database checks enforce `ends_at > starts_at`; presentation derives venue-local dates/times outside SQL storage contracts.
- All foreign keys below use `on delete restrict` unless a later owning ticket records a different lifecycle before its migration. Required lookup/foreign-key indexes are explicit rather than assumed from constraints.

### Role, RLS and credential matrix

| Principal            | Provisioning and ownership                                                                                                                | Allowed                                                                                           | Explicitly denied                                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Migration connection | Supabase CLI/local owner or separately supplied hosted migration credential; never loaded by application runtime                          | Apply checked-in migrations/seeds, create/alter objects and transfer `app` object ownership       | Browser/runtime use; inclusion in `.env.example` as a usable secret; logging or bundling                                             |
| `app_owner`          | Checked-in `NOLOGIN` role; owns `app` schema objects after migration                                                                      | Object ownership required for controlled migrations                                               | Direct application login and ordinary request execution                                                                              |
| `app_runtime`        | Checked-in `NOLOGIN`, `NOBYPASSRLS`, non-owner group role; an environment-specific login is provisioned out of band and granted this role | Connect, use `app` schema and execute only explicitly granted table operations through forced RLS | DDL, role management, schema ownership, Data API access, bypassing RLS or reading any private row while no policy/context permits it |

Every application table enables and forces RLS in DEV0015. No permissive runtime policy is added yet, so runtime-role queries against private tables return/affect no rows. DEV0016 owns verified subject/run transaction context and the first private policies. DEV0017 owns the separately restricted public catalogue role/path and its safe projections; DEV0015 does not create an unused public repository or anonymous policy.
